# ZYNQ PS 端推理结果通信格式技术说明

> 面向对象：负责 ZYNQ PS 端图像接收、PL 推理调度、后处理与结果返回的 FPGA 工程师。  
> 整理日期：2026-10-26。  
> 依据：本地项目中的树莓派接收源码。`FPGA/vision/transport/inference_client.py` 与 `Raspberry-for-JCS/circle-camera/dashboard_transport.py` 经逐字节比较一致。  
> 验证范围：源码核对、现有回归测试及本文件示例的解析验证；实板通信和模型数值精度需在现场联调。

## 1. 工程师先按这份接口实现

PS 端提供同步 HTTP 推理服务。树莓派上传一张图，PS 在同一次请求的响应中返回该图的推理结果。

| 项目 | 对接要求 |
| --- | --- |
| 服务地址 | `http://<ZYNQ_IP>:8080/predict`；端口和路径可通过树莓派配置调整 |
| 请求方法 | `POST` |
| 请求类型 | `multipart/form-data`，boundary 由 HTTP 客户端生成 |
| 图片字段名 | `image_file` |
| 图片格式 | JPEG；当前配置为 300×300，灰度图复制成三通道后编码 |
| 成功状态码 | `200 OK` |
| 成功响应类型 | `application/json; charset=utf-8` |
| 推荐响应结构 | 顶层 JSON 对象，含 `inference_ms` 和数组类型的 `result` |
| 每个候选的字段 | `class_name`、`score`、`loc` |
| 框坐标 | `loc = [x1, y1, x2, y2]`，相对于收到的 300×300 图片，通常用像素坐标 |
| 正常类别 | 建议统一为 `zheng_chang` |
| 缺陷类别 | 建议使用 `ca_shang`、`zang_wu`、`zhe_zhou`、`zhen_kong`；划痕使用中文 `划痕` |
| 错误响应 | 使用合适的 `4xx/5xx` 状态码，并返回错误说明 |

推荐成功响应示例：

```json
{
  "inference_ms": 18.4,
  "result": [
    {
      "class_name": "zhe_zhou",
      "score": 0.92,
      "loc": [30, 60, 90, 120]
    }
  ]
}
```

树莓派将其转换成：`NG`、缺陷数 `1`、类别 `折皱`，框的归一化坐标为 `x=0.1, y=0.2, w=0.2, h=0.2`。

本文中的“对接要求”用于约束 PS 新实现；“当前兼容行为”用于说明现有解析器的实际行为。解析器对部分错误数据较宽松，PS 输出仍应遵守明确的字段和数值要求。

## 2. 通信方向与模块职责

当前生产链路如下：

```text
树莓派相机 → 图像增强/圆检测 → 截取目标/缩放/JPEG 编码
    │
    └─ POST http://ZYNQ_IP:8080/predict
          文件字段：image_file
                    │
                    ▼
          ZYNQ PS：JPEG 解码 → 模型预处理 → 调用 PL/推理运行时
                    → 模型输出解码/后处理 → JSON 响应
                    │
                    ▼
树莓派：解析候选 → 阈值过滤/类别判定 → 看板存储与展示 → OK/NG 分拣调度
```

树莓派是 `/predict` 的 HTTP 客户端，ZYNQ PS 是 HTTP 服务端。当前链路通过以太网传输，不要求为推理结果另行实现串口、裸 TCP 或 UDP 报文。

树莓派另有 `POST /api/device/ingest`、`/api/device/result` 等看板接口。它们负责数据入库和页面展示。当前相机推理流程中，由树莓派在收到 `/predict` 响应后完成看板上传；PS 只需完成 `/predict` 请求与响应。直接向看板推送数据属于另一种接入方式，不能替代当前请求中的结果返回。

每次响应必须对应本次请求的图片。应完成推理后再返回结果，不使用 `202 Accepted + 任务 ID`、轮询或异步回调协议。树莓派不会按任务 ID 等待后续推理结果。

## 3. 树莓派发给 PS 的请求

### 3.1 实际请求内容

当前调用等价于：

```python
response = session.post(
    board_predict_url,
    files={
        "image_file": ("image_file.jpg", jpeg_bytes, "image/jpeg")
    },
    timeout=(0.5, board_request_timeout),
)
```

| 请求组成 | 当前内容 | PS 处理要求 |
| --- | --- | --- |
| 文件字段 | 默认 `image_file` | 解析 multipart 中该字段的文件内容 |
| 文件名 | `image_file.jpg` | 仅为固定文件名，不能据此区分样本 |
| 文件 MIME | `image/jpeg` | 按 JPEG 解码 |
| 普通表单字段 | 当前没有 | 不要求 `payload`、阈值、模型名、时间戳等字段 |
| `frame_id` | 当前没有传给 PS | 使用 HTTP 请求与响应的对应关系关联结果 |
| 自定义鉴权 | 当前调用没有设置鉴权头或令牌 | 如新增鉴权，需同步修改树莓派客户端 |

PS 应按表单字段名取文件，不应依赖某个固定 multipart boundary，也不应把整个 HTTP 请求体直接当成 JPEG。

### 3.2 图片尺寸、通道与预处理边界

1. 树莓派对灰度图中的目标区域截取带留边的正方形，超出原图的部分补黑。
2. 将截取区域直接缩放至当前配置的 `300×300`，使用 OpenCV `INTER_AREA`。
3. 将灰度值复制到 RGB 三个通道，按 JPEG 质量 `85` 编码后上传。
4. 未选到有效圆时，代码可回退为整幅灰度图再缩放；PS 仍以收到的图片为输入。

PS 收到的是 **JPEG 压缩文件字节**。客户端为后续看板记录生成的 `model_input.layout=NCHW`、`dtype=float32`、`tensor_shape=[1,3,300,300]` 等描述，并没有随 `/predict` 上传，也不表示网络上传输的是 float32 张量。

JPEG 解码后如何变成模型张量，由 PS 根据实际模型和推理运行时完成。通道顺序、归一化系数、均值/标准差、NCHW/NHWC、量化比例与零点均不能仅凭接收代码确定，须以模型导出及部署参数为准。若模型内部再次缩放或 letterbox，输出框必须映射回收到的 300×300 图片后再返回。

### 3.3 当前网络与超时配置

| 配置项 | 当前值或默认值 | 来源 |
| --- | --- | --- |
| 树莓派以太网 IP | `172.16.68.111/24` | `FPGA/config.sh` |
| 板端 IP 配置项 | `C5MB_IP=172.16.68.110` | `FPGA/config.sh`，变量名沿用原项目 |
| 推理 URL | `http://172.16.68.110:8080/predict` | `BOARD_PREDICT_URL` |
| 文件字段 | `image_file` | `BOARD_FILE_FIELD` 默认值 |
| 输入边长 | `300` | `BOARD_INPUT_SIZE` |
| JPEG 质量 | `85` | `BOARD_JPEG_QUALITY` |
| 候选置信度阈值 | `0.2` | `BOARD_SCORE_THRESH` |
| HTTP 连接超时 | `0.5 s` | `_infer_on_board()` |
| HTTP 读取超时 | `5.0 s` | 生产启动脚本的 `BOARD_REQUEST_TIMEOUT` 默认值 |

这些 IP 是源码中的现场配置，部署时以实际地址为准。ZYNQ 更换地址后需同步更新树莓派的推理 URL。PS 服务应监听树莓派能够访问的网口地址，例如 `0.0.0.0:8080`。

`5.0 s` 是 HTTP 读取等待超时，不是严格的整个请求总时限；不要将其视为允许每次推理耗时 5 秒的节拍目标。当前分拣延迟配置为 `3.40 s`，结果返回、看板上传和队列等待都会占用可用时间；实际节拍需结合现场输送和分拣时序确认。

## 4. 推荐 JSON 响应格式

### 4.1 顶层字段

| 字段 | 类型 | 本文对接要求 | 当前解析行为 |
| --- | --- | --- | --- |
| `result` | array | 必须提供；每项为一个正常或缺陷候选对象 | 优先作为候选列表解析 |
| `inference_ms` | number | 建议必须提供，有限且非负，单位毫秒 | 缺省或无法转为数值时，用树莓派测得的 HTTP 往返耗时代替 |

响应体须是 UTF-8 JSON **对象**。不要在 JSON 前后混入日志、HTML 或其他文本，不要返回裸数组，不要套成 `{"data": {...}}` 或 `{"results": [...]}`。当前解析器不递归寻找检测列表，也不识别 `results` 字段。

`result` 数组模式下，PS 不必另外提供 `defect_count` 或 OK/NG 字符串，最终判定由树莓派根据候选计算。同一个 JSON 对象中不能用两个 `result` 键分别表示字符串和数组。

### 4.2 候选对象字段

| 字段 | 类型 | 对接要求 | 示例 |
| --- | --- | --- | --- |
| `class_name` | string | 非空类别名称；按第 5 节统一 | `"zhe_zhou"` |
| `score` | number | 有限数值，范围 `[0,1]`；使用最终置信度 | `0.92` |
| `loc` | array[number] | 四个有限数值 `[x1,y1,x2,y2]` | `[30,60,90,120]` |

要求 PS 输出合法 JSON 数值，不使用 `NaN`、`Infinity`、百分数字符串或 `0～100` 的分数。`class_id` 不能代替 `class_name`：树莓派没有数字类别 ID 到名称的映射表。PS 必须根据实际模型的标签顺序完成 ID 到名称的转换，本文不规定模型类别 ID 的顺序。

正常类也可以作为候选返回，并参与与缺陷类的比较。若模型对正常类只有整图分类置信度、没有目标框，可按本接口约定使用整图框 `[0,0,300,300]`；该框只用于候选格式对齐，正常获胜后不会显示。此做法是给 PS 的实现建议，并非树莓派会自动补出的正常框。

### 4.3 三种常见成功响应

**检测到折皱：**

使用第 1 节的完整示例，树莓派输出 `NG`、`defect_count=1`。

**正常类别得分有效：**

```json
{
  "inference_ms": 17.8,
  "result": [
    {
      "class_name": "zheng_chang",
      "score": 0.96,
      "loc": [0, 0, 300, 300]
    }
  ]
}
```

树莓派输出 `OK`、`defect_count=0`、空检测框列表。

**推理成功，但没有需要返回的候选：**

```json
{
  "inference_ms": 16.5,
  "result": []
}
```

当前树莓派同样输出 `OK`。空列表必须代表一次成功完成的推理；模型未加载、推理异常或解码失败不能用空列表代替，错误返回方式见第 8 节。

## 5. 类别名称约定

### 5.1 建议固定使用的名称

| 业务类别 | 推荐 `class_name` | 接收端转换后的名称 |
| --- | --- | --- |
| 正常 | `zheng_chang` | 正常类获胜时不保留框 |
| 擦伤 | `ca_shang` | `擦伤` |
| 脏污 | `zang_wu` | `脏污` |
| 折皱 | `zhe_zhou` | `折皱` |
| 针孔 | `zhen_kong` | `针孔` |
| 划痕 | `划痕` | `划痕` |

也可统一使用中文名称：`正常`、`擦伤`、`脏污`、`折皱`、`针孔`、`划痕`。上表列出的是接口允许的业务名称；实际模型能否输出某类，仍取决于模型训练和标签文件。

### 5.2 当前 `/predict` 解析器已有别名

| 解析后的类别 | 接受的别名 |
| --- | --- |
| 擦伤 | `ca_shang`、`cashang`、`scratch`、`擦伤` |
| 脏污 | `zang_wu`、`zangwu`、`stain`、`dirty`、`脏污` |
| 折皱 | `zhe_zhou`、`zhezhou`、`wrinkle`、`fold`、`折皱` |
| 针孔 | `zhen_kong`、`zhenkong`、`pinhole`、`针孔` |
| 正常类别 | `zheng_chang`、`zhengchang`、`normal`、`ok`、`good`、`正常`、`良品` |

英文别名比较前会转为小写，名称两端空白会去除。

**必须明确的命名差异：** 当前板端结果解析器把 `scratch` 映射成 `擦伤`，而看板直接接入的标签映射把 `scratch` 映射成 `划痕`。为避免同一模型因接入路径不同而改变语义，PS 请按第 5.1 节输出；划痕明确使用中文 `划痕`。

当前解析器不会把未知名称判为非法，也不会根据数字 ID 补齐中文名；未知非正常标签可能被当作缺陷原样保留。不要使用 `0`、`1`、`class_0`、未约定的拼音或临时类别名。

## 6. 检测框的坐标要求

### 6.1 推荐 `loc` 形式

```text
loc = [x1, y1, x2, y2]
原点：收到的图片左上角
x：向右增加
y：向下增加
宽度：x2 - x1
高度：y2 - y1
```

对当前 300×300 输入，PS 应输出满足以下条件的矩形边界：

```text
0 <= x1 < x2 <= 300
0 <= y1 < y2 <= 300
```

`x2=300`、`y2=300` 可表示图片右、下边界。请按边界差值计算宽高，不额外加 `1`。数值可以是小数。

`loc` 不是 `[中心x,中心y,宽,高]`，也不是 `[x,y,w,h]`。若模型输出中心坐标格式，PS 应先转换：

```text
x1 = cx - w/2
y1 = cy - h/2
x2 = cx + w/2
y2 = cy + h/2
```

所有坐标均对应上传给 PS 的模型输入图片，不使用相机原始整帧坐标、裁剪前坐标、特征图网格坐标或 PL 内部张量坐标。

### 6.2 树莓派如何归一化

解析器先由 `loc` 生成 `x=x1, y=y1, w=max(0,x2-x1), h=max(0,y2-y1)`，然后按每个框分别判断：

```text
如果 max(abs(x), abs(y), abs(w), abs(h)) > 1.2：
    视为像素坐标
    x、w 除以输入图片宽度；y、h 除以输入图片高度
否则：
    视为已经归一化的坐标
```

最后四个分量分别限制到 `[0,1]` 并保留四位小数。它不根据 `normalized=true/false` 字段选择坐标模式，也不根据 PS 返回的 `frame.width/height` 改变分母；分母来自树莓派本次上传图片的实际尺寸。

例如 `[30,60,90,120]` 对应 300×300 图片，得到 `(x,y,w,h)=(0.1,0.2,0.2,0.2)`。

此处采用数值启发式，极小像素框如 `[0,0,1,1]` 会被误当作归一化整图框。若需要精确表达这种小框，请使用下述归一化 `bbox` 形式。PS 应自行检查非零面积和越界；当前代码可能保留零面积框，且分量独立截断不能替代完整的矩形边界校验。

### 6.3 兼容的归一化形式

除推荐的像素 `loc` 外，也支持以下格式：

```json
{
  "result": "NG",
  "defect_count": 1,
  "inference_ms": 18.4,
  "detections": [
    {
      "label": "针孔",
      "confidence": 0.96,
      "bbox": {"x": 0.1, "y": 0.2, "w": 0.2, "h": 0.2}
    }
  ]
}
```

这里的 `x,y` 是左上角，`w,h` 是宽高，四项均相对于输入图片归一化。应满足 `w>0`、`h>0`、`x+w<=1`、`y+h<=1`。`bbox` 必须是对象，不是数组。每个候选选择一种坐标形式即可，避免同时提供 `loc` 与 `bbox`。

## 7. 树莓派的最终 OK/NG 判定规则

### 7.1 实际处理顺序

1. 读取候选数组，跳过非对象元素和没有有效类别名称的候选。
2. 删除 `score < BOARD_SCORE_THRESH` 的候选；默认阈值 `0.2`，等于 `0.2` 时保留。
3. 转换类别别名和框坐标，将置信度保留四位小数。
4. 在所有剩余候选中比较置信度，正常类和缺陷类一起参与。
5. 选择全局最高置信度候选所属的类别。
6. 正常类获胜：输出 `OK`，清空检测框，缺陷数为 `0`。
7. 缺陷类获胜：只保留该获胜类别下所有达到阈值的框，输出 `NG`，缺陷数为保留框数量。

比较置信度发生在四位小数舍入之后；非常接近的原始分数可能因此成为同分。正常与缺陷同分时缺陷优先；两个不同缺陷类别同分时，按响应列表顺序选择先出现的类别。同一获胜类别的保留框维持原返回顺序。

树莓派的这一步是类别选择，不是基于 IoU 的 NMS。模型所需的输出解码、量化值恢复、候选生成和 NMS 等后处理由 PS/模型运行时完成。重复框不会由这里自动去重，会影响缺陷计数。

**不要仅因出现任意一个缺陷框就认定最终 NG。** 正常候选若比所有缺陷候选得分高，当前系统会判 OK。PS 应保留需要参与最终比较的有效类别候选，不能为了简化输出而提前删除正常类别。

### 7.2 示例：只保留获胜类别的有效框

```json
{
  "inference_ms": 18.4,
  "result": [
    {"class_name": "zhe_zhou", "score": 0.92, "loc": [30, 60, 90, 120]},
    {"class_name": "zheng_chang", "score": 0.90, "loc": [0, 0, 300, 300]},
    {"class_name": "zhe_zhou", "score": 0.20, "loc": [150, 60, 210, 120]},
    {"class_name": "zhe_zhou", "score": 0.19, "loc": [220, 60, 250, 90]},
    {"class_name": "zhen_kong", "score": 0.80, "loc": [30, 150, 60, 180]}
  ]
}
```

最终为 `NG`、类别 `折皱`、缺陷数 `2`；保留 `0.92` 和 `0.20` 的折皱框，删除 `0.19` 的折皱框，并不展示针孔框。

### 7.3 空列表、无效候选和显式结果

| 响应情况 | 当前树莓派结果 |
| --- | --- |
| 正常 `0.91`，折皱 `0.28` | `OK`，0 个框 |
| 正常 `0.90`，折皱 `0.90` | `NG`，保留折皱框 |
| 折皱 `0.90`，针孔 `0.90`，折皱先出现 | `NG`，保留折皱类别 |
| 所有候选低于 `0.2` | `OK`，0 个框 |
| `result=[]`，未提供其他有效判定 | `OK` |
| 候选列表非空，但每个候选均被跳过或过滤 | `OK`，即使同时写了字符串 `result="NG"` |
| 没有非空候选列表，且字符串 `result="NG"` | `NG`，缺陷数至少为 1 |
| 没有候选也没有可识别的 OK/NG，例如 `{}` | 默认 `OK` |

因此，非法候选和错误 JSON 对象不能当作错误信号返回；PS 必须使用错误 HTTP 状态码。

## 8. 时延、错误处理与执行结果

### 8.1 时延字段

`inference_ms` 用于表示板端推理耗时。建议 PS 以单调时钟测量实际 PL/推理运行时执行阶段，用浮点毫秒返回；若将预处理或后处理也计入，应在联调记录中明确计时范围，保证各次测量口径一致。

树莓派另外测量从发起 HTTP 请求到完整读取响应体的耗时，记为 `board_roundtrip_ms`。它包含网络、PS 解码/预处理/推理/后处理、响应传输等时间，不应当作纯模型耗时。

若 PS 不返回有效的 `inference_ms`，树莓派会把往返时间同时用于 `board_inference_ms`，看板上的“纯推理”数值就不再代表实际模型计算时间。只放一个自定义响应头 `X-Inference-Ms` 不会被当前接收代码读取。

### 8.2 错误响应要求

建议的错误码如下；这些是给 PS 的实现约定，现有树莓派只统一将 HTTP 错误状态视为失败，并不按业务错误码细分处理。

| 场景 | 建议 HTTP 状态码 |
| --- | --- |
| 缺少 `image_file`、图片损坏或尺寸参数不合法 | `400 Bad Request` |
| 不支持的文件媒体类型 | `415 Unsupported Media Type` |
| 模型未加载、推理资源暂不可用 | `503 Service Unavailable` |
| PL/运行时推理异常、后处理异常 | `500 Internal Server Error` |

例如模型未就绪时返回 `503`，响应体可使用：

```json
{
  "error": "MODEL_NOT_READY",
  "message": "Inference model is not loaded"
}
```

**不能以 HTTP 200 返回上述错误对象。** 当前解析器能读到顶层 JSON 对象时会进入结果解析；如果其中没有候选或显式 OK/NG，默认结果是 `OK`。同理，`{"success":false}`、`{"code":500}`、`{"status":"error"}` 本身不能让当前客户端认定推理失败。

连接异常、读取超时、HTTP `4xx/5xx`，以及既不是 JSON 对象又没有 `X-Has-Defect` 头的响应，会进入板端推理失败分支。当前流程不会自动重试同一张图片，也不会把推理异常自动改判成 `NG`。

### 8.3 与分拣的关系

推理结果成功解析后，树莓派再上传看板；生产配置下，上传也成功才会将最终 OK/NG 加入机械臂动作队列。当前 `ACTION_DIRECTION_MODE=0` 对应 `NG→左`、`OK→右`，该方向由树莓派配置控制。

PS 返回推理判定即可，不需要在此接口中返回左右方向或机械臂指令。HTTP 200 和合法响应表示本次推理接口成功，不构成机械臂已经完成动作的确认。

## 9. 已兼容的其他 JSON 形式

为了联调时能够识别现有板端实现，以下列出现有兼容规则。新实现建议固定使用第 4 节的形式。

| 内容 | 查找顺序/规则 |
| --- | --- |
| 候选列表 | 数组类型 `result` → 数组类型 `detections` → 数组类型 `boxes`，只读取第一个匹配的列表 |
| 类别名称 | `class_name` → `label` → `name` → `category`，读取第一个非空值 |
| 置信度 | `score` → `confidence` → `probability`，按键是否存在取值 |
| 坐标 | 有效数组形式 `loc` 优先；否则取对象 `bbox` 的 `x,y,w,h`，缺项可回退顶层同名字段 |
| 右下角补充 | 在 `bbox` 分支缺少 `w/h` 时，可用候选顶层 `x2/y2` 减去 `x/y` |
| 显式 OK/NG | 无非空候选时，允许字符串 `result` 为 `OK` 或 `NG`，忽略大小写和两端空白 |
| 显式缺陷数 | 仅无保留框且显式判 NG 时使用 `defect_count`，最少为 1；有保留框时按框数重算 |

注意：`result=[]` 会遮蔽同一对象中的非空 `detections` 或 `boxes`。`score:null` 也不会自动改读另一个 `confidence` 值。因此每个语义固定使用一个字段，避免重复别名。

只做 OK/NG 演示时，以下形式也能解析，但不提供类别或缺陷位置：

```json
{
  "result": "NG",
  "defect_count": 1,
  "inference_ms": 18.4
}
```

`defect_count` 单独大于零并不足以使 `/predict` 解析器判 NG，必须有有效缺陷候选或显式 `result="NG"`。不要把看板直接入库接口的宽松规则当成此推理接口规则。

## 10. 备用模式：返回图片和 `X-Has-Defect` 响应头

当前客户端还兼容以下响应：

```http
HTTP/1.1 200 OK
Content-Type: image/jpeg
X-Has-Defect: 1

<JPEG 图片二进制>
```

| 响应头值 | 当前解释 |
| --- | --- |
| `1`、`true`、`yes`、`y`、`ng`、`defect`、`bad` | NG，缺陷数固定为 1 |
| `0` | OK，缺陷数为 0；推荐只用 `1/0` |
| 其他任何值 | 当前均按 OK 处理，工程实现不要使用 |

值比较前会去除首尾空白并转为小写。响应体若被识别为图片，会作为板端结果图片传给看板；判断依据为 `Content-Type` 以 `image/` 开头，或响应体具有 JPEG/PNG 文件头。

该模式没有结构化类别、置信度和检测框，无法精确表达多个缺陷，推理耗时也只能回退为 HTTP 往返耗时。需要缺陷明细和统计时应使用 JSON 模式。

响应解析优先级为：先尝试读取顶层 JSON 对象；成功则只走 JSON 逻辑。只有未读到 JSON 对象时才检查 `X-Has-Defect`。例如 HTTP 200、`X-Has-Defect: 1` 与响应体 `{}` 同时出现，当前结果仍为 OK。只返回 JPEG、不带该响应头，会被视为推理失败。

## 11. PS 实现顺序与联调验收

### 11.1 建议的 PS 主处理流程

```text
收到 POST /predict
  → 从 multipart 获取 image_file
  → 校验文件、解码 JPEG，按约定检查输入尺寸
  → 按实际模型要求构造输入张量
  → 调用 PL/推理运行时，测量推理时间
  → 解码模型输出，执行所需后处理，将 class_id 转为约定名称
  → 将框还原到收到的图片坐标，检查分数和框的合法性
  → HTTP 200 返回 {inference_ms, result:[{class_name,score,loc}, ...]}
任一步失败
  → 返回相应 4xx/5xx 和错误说明
```

HTTP 层可先使用固定推理结果完成联调，再替换成真实模型输出。模型专属的输入量化、输出张量布局、锚框/先验框、NMS 参数以及 PL/PS 调用方式，需要模型工程资料支持，不能从树莓派接收格式反推出。

### 11.2 手工请求

在树莓派或能访问 ZYNQ 的电脑上，准备真实的 300×300 JPEG 文件 `sample_300.jpg` 后执行：

```bash
curl --fail-with-body -i \
  -F 'image_file=@sample_300.jpg;type=image/jpeg' \
  'http://172.16.68.110:8080/predict'
```

此命令直接调用推理服务。curl 会自动生成 multipart boundary，不要手工指定不含 boundary 的 `Content-Type: multipart/form-data`。没有 `--fail-with-body` 的旧 curl 可改用 `-i` 查看 HTTP 状态码。
